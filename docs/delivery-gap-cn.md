# CalmWay 距离最终可交付版本的剩余工作

当前仓库是一个可以运行的大学实践项目脚手架，不是最终的 Part 2 可交付版本。现有实现用于验证基本界面、前后端结构和团队协作方式；真实数据、真实路线比较及部署仍需后续完成。

## 当前已经完成

- React、Vite、TypeScript 前端脚手架
- FastAPI 后端脚手架
- 前后端联通
- 模拟路线接口
- 路线卡片界面
- LOW、HIGH 感官等级显示
- 推荐路线显示
- 英文表单验证
- 接口错误处理
- pytest 测试
- 文档结构
- `data/raw/` 和 `data/processed/` 占位目录
- `scripts/process_data.py` 占位脚本
- `pedestrian_service.py` 占位服务
- `sensory_service.py` 临时感官等级服务

## 最终可交付前必须完成

### 1. 最终数据集确认

数据科学团队仍需提供：

- 最终选定的行人数据集
- 处理后的数据文件
- 文件格式
- 字段定义
- 数据来源
- 更新频率（如已知）
- 缺失值处理说明
- 建议的拥挤度或感官等级阈值

在数据集正式确认前，不应自行假设或编造实际字段名称。

### 2. 数据处理脚本实现

当前的 `scripts/process_data.py` 只是安全的占位脚本，不会读取或转换数据。

最终脚本应根据已选定的数据集真正执行以下流程：

```text
原始数据
  → 清洗
  → 验证
  → 转换
  → 处理后数据
```

具体处理规则必须以真实数据及数据科学团队的说明为依据。

### 3. 实现 pedestrian_service.py

当前 `pedestrian_service.py` 只保留了服务职责和占位接口。

最终版本需要读取处理后的行人数据，并向后端其他服务提供可用的行人信息。由于最终数据集尚未确认，目前不应预先确定文件读取方式、字段映射或返回结构。

### 4. 实现 sensory_service.py

当前版本只为模拟路线返回固定的感官等级。

最终版本应使用基于处理后行人数据的规则逻辑，概念输出为：

- LOW
- MEDIUM
- HIGH
- UNKNOWN

当前实践范围不要求机器学习。实际阈值应在数据科学分析完成后确定，缺失数据不能自动视为 LOW，应使用明确且安全的缺失数据处理规则，例如返回 UNKNOWN。

### 5. 实现真实路线逻辑

当前 Route A 和 Route B 都是模拟路线。最终版本至少需要一种真实的路线比较机制，可考虑以下两种简单方案：

**方案 A：使用外部或开放路线服务**

使用步行路线服务生成路线选项，再将路线与行人数据结合。采用此方案前需要确认服务限制、接口稳定性和团队集成成本。

**方案 B：使用预定义的墨尔本中央商务区路线片段**

在较小的实践范围内，预先定义有限的路线片段，并与真实行人数据结合。对于本次大学实践迭代，该方案可能更简单、风险更低。

本文档不自动选择方案。团队应根据时间、数据可用性和评估要求共同决定。

### 6. 替换模拟路线结果

当前 Origin 和 Destination 会传给后端，但返回的路线结果实际上不依赖这些输入。

最终流程应为：

```text
用户输入
  → 路线逻辑
  → 行人数据
  → 感官等级计算
  → 推荐路线
  → 前端显示
```

完成该流程后，应移除当前固定的 Route A 和 Route B 模拟数据。

### 7. 更新真实数据逻辑测试

当前测试只验证脚手架和模拟行为。后续测试应覆盖：

- 数据加载
- 感官等级分类
- 接口使用处理后数据
- 缺失数据处理
- 路线推荐

测试套件应保持小而清晰，符合大学实践项目的规模，不需要扩展为复杂的生产级测试体系。

### 8. 部署

`http://localhost:5173` 和 `http://127.0.0.1:8000` 都只是本地开发地址。

最终 Part 2 需要提供可以访问的已部署网页链接。部署平台目前尚未决定，应在真实数据和路线流程稳定后再选择合适的平台。

### 9. 最终交付前更新文档

真实数据和路线逻辑完成后，必须同步更新 `README.md` 和 `docs/` 中的文档。所有描述为以下状态的内容都需要删除或修订：

- `mock`（模拟）
- `placeholder`（占位）
- `not implemented`（尚未实现）

文档必须准确反映最终实际功能，不能继续声称已经被替换的模拟行为仍在使用。
